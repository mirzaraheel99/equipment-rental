# Decision Register

**Purpose:** Formal record of decisions made against the "Open Decisions Before Execution" list in `docs/09-Implementation/25-IMPLEMENTATION-PACK-01-PROJECT-BOOTSTRAP.md` §33, plus other cross-cutting decisions made during planning. Each entry is dated, gives the decision, the rationale, and the alternative(s) considered. This register is append-only — a changed decision gets a new row referencing the old one, not an edit in place, consistent with the audit-trail conventions used throughout this repository.

---

## Bootstrap Technical Decisions (Implementation Pack 01 §33)

| # | Decision Area | Decision | Rationale | Alternative Considered |
|---|---|---|---|---|
| 1 | Node.js version | **22 LTS**, pinned via `.nvmrc`, `.node-version`, and `package.json` engines | Doc 25's own recommendation; actively maintained LTS at time of writing | Node 24 (also LTS by mid-2026) — deferred; no concrete need to move off 22 yet, revisit at Phase 20 hardening |
| 2 | pnpm version | Latest stable pnpm 9.x, pinned via `corepack` | Doc 25's own recommendation; strong workspace support for a large TS monorepo | npm/yarn workspaces — rejected, weaker monorepo ergonomics |
| 3 | Monorepo orchestration | **Turborepo**, confirmed | Doc 25's own recommendation; simple build graph, good Next.js/TS compatibility | Nx — rejected as higher overhead than justified at this stage |
| 4 | ORM | **Prisma** | Stronger migration-diffing and schema-review ergonomics for a team following the roadmap's strict "migration reviewed / constraints present / indexes reviewed" data gate (doc 24 §4.3); mature NestJS integration | Drizzle — lower-level, faster raw queries, but weaker migration-review tooling for this team's process |

| 10 | NestJS version | Latest stable | Doc 25's own recommendation | — |
| 11 | Tailwind version | Latest stable v4 | Greenfield project; v4's CSS-based config reduces boilerplate | Tailwind v3 — rejected, no reason to start on the older major version for a new build |
| 12 | Local object storage | **MinIO** | Doc 25's own recommendation, S3-compatible, matches CLAUDE.md's S3-compatible object storage architecture direction | — |

| 18 | Mobile PWA as separate app | **No, not yet** — mobile-first workflows (driver, technician, yard, checkout/return) ship as responsive routes inside `apps/web` | Doc 25's own target repository tree (§5) omits a separate `mobile-pwa` app, even though the roadmap's high-level structure (doc 24 §3) lists one aspirationally; deferred until an offline-first requirement actually justifies the split | Separate `apps/mobile-pwa` from day one — rejected as premature per doc 25 §32.1 "Premature Dependency Growth" risk control |

| 21 | Customer scope | **B2B/corporate-first**: build corporate/project customer and contract workflows as the primary near-term target; keep "Individual" as a supported customer type in the data model, no consumer self-checkout UX yet | User-approved; matches the market research doc's segment analysis and the user's own emphasis on long-term corporate contracts | 2026-07-30 |
| 22 | Doc numbering for newly authored domain docs | Where a new domain doc's subject matches a named roadmap phase (doc 24), its filename number is aligned to that phase number for mnemonic consistency (Asset Registry=05↔Phase 05, Pricing=08↔Phase 08, Rental Operations=11↔Phase 11, Maintenance/PPM=13↔Phase 13) | Existing docs 06/07 don't follow this convention perfectly (Contract doc is numbered 07 but is Phase 09) — not retroactively renumbered to avoid breaking existing cross-references; new convention applied going forward only | 2026-07-30 |
| 23 | Primary key generation | **Application-generated UUIDv7** (`uuid` npm package, `v7`), no database-side default | UUIDv7 is time-ordered, so it avoids the index-fragmentation cost of random UUIDv4 while still being generatable client-side (no round-trip to get an ID before writing related rows/outbox messages in the same transaction); matches the database dictionary's stated PK preference (`docs/06-Data/18-ENTERPRISE-DATABASE-DICTIONARY.md` §3) | 2026-07-30 |
| 24 | Interim tenant-resolution mechanism (Phase 02) | Tenant scope for Platform Core is resolved from an `x-tenant-id` request header, validated against an active `Tenant` row, and bound via `AsyncLocalStorage` for the request's lifetime; a Prisma Client Extension then structurally enforces that scope on every query | The database dictionary (§4.2) requires tenant scope to never be client-supplied as the authoritative source — this header mechanism is explicitly interim, documented as such in code (`apps/api/src/tenant/tenant.middleware.ts`), and is scheduled for replacement by auth-derived tenant scope in Phase 03 (Authentication/RBAC). No RBAC guard exists yet on the Phase 02 organization endpoints for the same reason — anyone with a valid tenant header can currently reach them. | 2026-07-30 |
| 25 | CHECK constraints on hand-authored migration SQL | Enum-like columns (`tenant.tenant_type`, `tenant.status`, `legal_entity.status`, `branch.branch_type`, `branch.status`, `department.status`) get a hand-appended `ALTER TABLE ... ADD CONSTRAINT ... CHECK (... IN (...))` at the end of the Prisma-generated migration file, rather than being left to application-layer validation alone | Prisma's schema DSL has no stable CHECK-constraint syntax as of Prisma 7; the database dictionary requires these columns be constrained at the database level, not just validated in DTOs, so the gap is closed by hand in the generated SQL and the enum's allowed values are kept in sync with the corresponding `class-validator` DTO's controlled-vocabulary tuple | 2026-07-30 |
| 26 | **Supersedes #24** — Tenant scope resolution (Phase 03) | Tenant scope is now derived from the verified access token's `tenantId` claim (set by `AuthMiddleware`), never a client-supplied `x-tenant-id` header. The interim header mechanism (`tenant.middleware.ts`) is removed. | Auth domain doc (03) §5.3 explicitly plans this as Phase 03's replacement of Decision #24 — not a change of direction, the scheduled one | 2026-07-30 |
| 27 | Authentication model — federated OIDC only, no local password store | `user_account` has no `password_hash` column in the database dictionary (§7.1), and `external_identity_id` is a first-class column — the dictionary's implicit design is federated identity via an external OIDC issuer, never a password ERMS itself verifies | Adding an undocumented `password_hash` column was rejected as inventing schema the dictionary doesn't specify (CLAUDE.md's "do not invent tables/requirements" rule); a `LocalDevProvider` stub OIDC issuer gives a working dev/CI login flow instead (Auth domain doc (03) §5.1) | 2026-07-30 |
| 28 | Access-token content — identity only, no embedded permissions | The JWT access token carries only `{sub, tenantId, audience}`; every authorization check re-queries `role`/`permission`/`role_permission`/`user_role_assignment` fresh per request | Required for the roadmap's "revoked role" test case to actually work — a claim cached in a token can't reflect a revocation until the token expires; database-sourced authorization reflects it on the very next request | 2026-07-30 |
| 29 | Refresh token storage | Opaque random value in Redis (`refresh:{tokenId}`), rotated on every use, not a JWT and not a new Postgres table | The database dictionary has no session/refresh-token table; Redis is already an architecture-direction dependency (CLAUDE.md) and is the natural fit for short-lived, high-churn, revocable session state | 2026-07-30 |
| 30 | Password/credential hashing library | Not applicable — no password store exists (see #27); `argon2` was considered but not adopted since there is nothing to hash | — | 2026-07-30 |
| 31 | JWT signing | `@nestjs/jwt` (wraps `jsonwebtoken`) for ERMS's own access tokens; `jose` for verifying externally-issued OIDC ID tokens (Entra ID's JWKS-based verification) | `@nestjs/jwt` is the idiomatic Nest choice for a service's own tokens; `jose` has first-class remote-JWKS support needed to verify a real external issuer, which `@nestjs/jwt` does not provide | 2026-07-30 |

## Governance Note

Per CLAUDE.md and the roadmap's "no silent assumptions" rule, every decision above is a **default proposal**, not a claim of business sign-off. Items with material commercial or legal weight (e.g. license allowlist, dependency-update policy) should be re-confirmed by the actual business/legal stakeholders before Stage 2 (Bootstrap) code is merged to a protected branch, even though they are treated as approved-for-now to unblock scaffolding.
